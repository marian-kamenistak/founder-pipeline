# P4.S3 — Web build → `P4-Build.S3-Web.md` + project `web/` folder

**Phase: P4-Build**

**Earns its keep when** the format decision in P4.S2 includes a web surface. **Skip entirely** (with one line in `brief.md` saying why) when the stream is deck-only or app-only. A stream that sells entirely through warm outreach and has no page to send anyone to skips this step and P4.S4 with it — that is a normal outcome, not a shortfall.

**Hard gates:**
- ~~Pre-sale gate~~ **removed. The web builds in every run — and in OVERNIGHT runs P4.S3 is a MUST-HAVE step: build AND deploy live, with the URL + diff + rollback note in the morning review.**
- **Copy sources section of `P4-Build.S2-Copy.md` approved by the owner** (overnight: fresh-judge-passed, flagged for morning approval). Builders lay out and style; they do not write copy.

## Default stack — the house stack, declared once

**Every web build in this pipeline goes through `/web-site-creator`, on the house stack declared at P1.S1.** The recommended default — and the stack the recipes below are written against — is **a static-first framework on an edge platform: Astro 5 + Cloudflare Workers**. Whatever you declared at P1.S1 is what every stream uses; **a web build outside your declared house stack is an anti-pattern**, allowed only when the owner explicitly overrides for a specific stream and the override is recorded in `P2-Viability.S2-Tooling.md` with the reason.

The point of the rule is not the framework. It is that a solo operator maintaining four streams on four stacks maintains nothing. Pick one, declare it, and let "we already know how to do this" be the compounding asset.

**Where the stack is named below** — Astro, Cloudflare Workers, Turnstile, a transactional sending API, a product-analytics tool — read it as *the capability*, and substitute your stack's equivalent. The capability is the requirement; the vendor is the example.

**Brand kit — apply the configured one silently, do not ask.** Every stream web build uses **the brand kit configured for the stream** (or the estate default, if you keep one). A kit is a folder holding: `DESIGN.md` (the written design system — voice of the visuals, layout rules, component inventory), `tokens.css` + `tokens.json` (colour, type scale, spacing, radii, shadows as machine-readable values), and `screenshots/` (full-page references of the surfaces the kit already produced). Point `/web-site-creator` at that folder as its design input.

Apply it without asking for confirmation — the only way a different kit gets used is the owner explicitly naming one (in the kickoff or mid-run), and that override is recorded in `P2-Viability.S2-Tooling.md`. Do **not** re-extract tokens for a brand whose kit already exists; the kit is the source of truth. If the stream is a genuinely new brand with no kit, building the kit is step 2 below and it happens *before* the site, not during it.

**Delegate the build (context-budget hard rule — see SKILL.md House rules).** The actual site build MUST be delegated: spawn ONE build subagent that runs `/web-site-creator` and reads the copy sources (`P4-Build.S2-Copy.md`), the brand kit, and the keyword contract (`P4-Build.S1-Keywords.md`) ITSELF on its own context, then returns ONLY a compact build-log summary — live URL, the hardening/SEO error table, a per-page rendered-text-vs-Copy-sources diff verdict (page | match/deviation | quote) appended to the build log (so the 1:1 copy-match criterion is checked by artifact, not vibe), and any open placeholders with owners. The main context MUST NEVER hold the page copy or the audit/Lighthouse transcripts — only the returned summary and the gate verdict below. The flow below is the contract that subagent works to.

**Flow (high-level — `/web-site-creator` is the contract and has the full spec):**
1. **Invoke `/web-site-creator`** and work its phases top to bottom, passing the brand kit folder as the design input.
2. **Design tokens**: copy from the existing kit by default. Only for a NEW brand: extract them — from a reference URL with `/firecrawl-scrape` (pull the rendered page, read its computed palette, type scale and spacing off the CSS), or from a brand book PDF (read the PDF directly and transcribe the values). Either way the output is a **new kit** — `tokens.json` + `tokens.css` + `DESIGN.md` + full-page screenshots — written into your brand-kit store *before* the site build starts. Kits are reusable; one-off extractions are not, and a build that skips the kit leaves the next stream re-doing this work.
3. **Scaffold** the house stack per `/web-site-creator` Phase 1.1 (recipe: its `references/core.md` §2). CI-based deploy from the repo, preview per branch.
4. **Build primitives + pages** (home, product, pricing, about, blog, contact as applicable). Copy comes verbatim from the approved Copy sources section of `P4-Build.S2-Copy.md`; any new copy routes through `/brand-voice` and back into the Copy sources section of `P4-Build.S2-Copy.md` first.
5. **Animations + transitions** — a lightweight animation library plus the framework's own view transitions; motion budget enforced.
6. **Forms** — a bot check (CAPTCHA/Turnstile-class), a transactional sending API, and a **server-side schema-validated** endpoint. Client-side validation is a UX nicety; the server-side check is the security boundary. Never accept an unvalidated form POST because the front end already checked it.
7. **Email authentication DNS — SPF + DKIM + DMARC (explicit step, never skip — `/web-site-creator` Phase 3.2; recipe: its `references/interactivity.md` §16.6).** The moment the site sends mail (the transactional API + any human mail from P4.S0), the domain needs all three or mail spams and the domain is spoofable. Inventory every `@brand.com` sender first; publish exactly ONE root SPF TXT + ONE `_dmarc` TXT + each sender's own DKIM selector (all DNS-only records, no proxying); set DMARC to `p=none`, monitor 1–2 weeks until every legitimate sender shows an aligned pass, then ramp `none → quarantine → reject`. Never jump straight to reject. **P4.S0 already published the human-mail records and recorded the merged root SPF value — cite it and match it here; do not publish a second root SPF TXT.** (BIMI/VMC is a separate later brand decision, not part of the build.)
8. **SEO + AI SEO**: full meta spec, JSON-LD recipes per surface, favicon set, hreflang, geo meta, `robots.txt`, `llms.txt`, `llms-full.txt`, agent-discovery endpoint. **Entity schema (do not skip for a person/org brand):** the About page ships `Person` and/or `Organization` JSON-LD with a `sameAs` array listing the SAME canonical profile set the brand uses everywhere — its social profiles, code hosting, company directories, and the Wikidata Q-item once it exists (post-launch). This is entity consolidation, not a backlink; it is how Google's Knowledge Graph and LLMs resolve who the brand is. Keep the `sameAs` set identical across every stream's About page — mismatches weaken entity resolution.
9. **MCP server** (optional but recommended if the brand wants to be usable by agents): scaffold one hosted at `/mcp`, with discovery at `/.well-known/mcp.json`. `/cloudflare:build-mcp` does this on Workers if you have the `cloudflare` plugin installed — an **optional separate install**, not bundled with this plugin; any MCP server framework works.
10. **Instrument product analytics** before launch. This step OWNS the analytics wiring (once); P6.S2 owns the metric definitions read from it — it never re-instruments. `/posthog:instrument-product-analytics` covers this if you have the `posthog` plugin installed (again an optional separate install); otherwise wire your analytics tool by hand, to the same rule: the events exist before the first visitor, not after. **Scope = every user-facing surface the stream ships, not only the site:** standalone apps, Workers or services on their own routes, tools, MCP endpoints. A surface with no analytics makes the P5.S1 day-0 baseline and every P6.S2 read `unmeasured` (in one run a companion app lived on its own route with zero analytics code, so its usage could not be baselined at all). Confirm the analytics tool is pointed at the stream's own project before verifying the test event — an MCP or CLI pinned to a sibling project returns a clean zero.

**Free-tool / lead-magnet page rule (applies to EVERY interactive tool page: calculator, quiz, test, wizard).** Each tool page ships with TWO conversion elements below the tool, both mirrored into every language the page ships in:
1. **Services CTA block** — pitches the stream's paid offer off the tool's own result ("want my read on your result?" shape), with one button to the booking or enquiry destination. **Never ship a tool page whose only exit is the PDF/email gate.** A visitor who just got a number from you is the warmest they will ever be; sending them only to an email form spends that moment on a list subscription.
2. **Tiny email-capture form** — one field plus a honeypot, framed as a callback promise rather than a newsletter signup, POSTing to the stream's capture endpoint. **Keep the capture's `source` value distinct from the source patterns your lead-magnet delivery matches on.** This is a real failure mode, not a hypothetical: a capture endpoint that routes by regex on `source` will silently fire a magnet-delivery email at someone who asked for a callback, if the tool page's source string happens to match the magnet's pattern. Name tool-page captures with their own prefix and check the delivery rules before shipping.

Build both as **one reusable component** taking language and source as props (a services pitch wrapping a compact capture form), so every tool page gets the pair by construction rather than by remembering. Article and blog templates get the equivalent through an **unconditional** services CTA in the renderer — a tag-to-offer map with a default-offer fallback — so no post can ship CTA-less. The homepage gets at most a compact tools strip placed BELOW the primary conversion CTAs, instrumented, never above them.

**Location rule — the web lives in the project's `web/` folder.** The canonical, editable web sources for the stream (page files, `llms.txt`, any page-specific assets) live at `<project>/web/` inside the stream's own repo — NOT inside a shared pipeline repo. If the page deploys through a shared app (one site serving several streams under different routes), the project's `web/` folder holds the source of truth plus a `deploy.sh` that syncs the files into the shared app, builds, and deploys — so edits happen in the project, the shared repo is a build target, and the stream's repo shows the full web state to anyone who opens it. Include a `README.md` in `web/` documenting the architecture, routing, and open placeholders.

## Post-build hardening pass (always run before driving traffic)

These run AFTER the asset is built and BEFORE activation (P5.S1–S2) or the P6.S1 channels send traffic at it. Skip none unless the asset will never receive organic search traffic — and document the skip + why in `P4-Build.S2-Copy.md`.

| Concern | How | When |
|---|---|---|
| **Technical SEO + on-page** | `/seo-audit` | Always for any page that should rank. Output: `marketing/seo-meta.md` (or a stream-scoped variant) with title + description + OG card spec + HTML meta block + JSON-LD per page. |
| **AI-search visibility** | `/ai-seo` | If the GTM expects citations from AI answer engines. |
| **`llms.txt` + `llms-full.txt` quality** | `/ai-seo-llms-builder` | Always when the stream ships either file. Owns their structure plus the extractability of the money pages they route to. Carries the evidence that `llms.txt` is agent-context, not a ranking lever, so nobody budgets it as one. |
| **Web performance** | Lighthouse (or your CI's equivalent) on mobile, plus a Core Web Vitals, caching and image-optimisation pass. `/cloudflare:web-perf` covers this if you have the `cloudflare` plugin installed — an optional separate install. | 95+ mobile gate per `/web-site-creator`. |
| **Voice consistency final pass** | `/brand-voice` | Re-run on every reader-facing string before publish. Cheap insurance against AI-smooth drift sneaking in during build. |
| **Design + content review** | A pre-publish review pass, by a fresh reviewer (human or a subagent given only the live URL and the brand kit). Checks: does every page state have a designed empty/loading/error case; is the primary action unambiguous above the fold; does the visual hierarchy match the task hierarchy; does it hold at 375px; are the kit's tokens actually used rather than approximated; does any string still read as a placeholder. | Always, before the gate below. |

**Hardening output — ONE severity-ranked SEO/GEO error table (mandatory).** Merge every finding from the rows above into a single table in the build log — columns: `SEO/GEO error type | Severity | Fix | Status`, sorted High → Moderate → Low. **High** = blocks ranking or AI citation (missing/duplicate meta description, missing JSON-LD, noindex leak, broken hreflang, unreachable `llms.txt`). **Moderate** = weakens it (meta descriptions too short, thin inbound links from quality domains, missing FAQ schema, weak internal linking). **Low** = polish. Gate: **zero High rows open at sign-off**; each Moderate row is either fixed or carried into `P6-Adoption.S2-KPIs.md` with an owner + date — never silently dropped. Re-run the table after any later content or structure change (the same rule the project's own post-change instructions should carry) — **P4.S4's fix pass is such a change: its re-run is appended to this file with a date.**

**Post-launch — launch + links execution: P5.S1–S2.** Search-console and IndexNow submissions, business-listing profiles, day-0 rank baseline, backlink-gap outreach execution, directory submissions, content cadence, and the 90-day loops all moved OUT of this step — P5.S1 (launch) and P5.S2 (links) execute them; `references/web-post-launch.md` is their reference, not this step's. What STAYS here (it is build/implementation, not launch): every money page ships the AI-extractability kit (`references/dataforseo-playbook.md` Job 7.6) — a definition block in the first 300 words, an FAQ block plus `FAQPage` JSON-LD, one comparison table, a synonym-first title — and per-page on-page verification runs before sign-off (an on-page crawl API such as DataForSEO's `/v3/on_page/instant_pages` if you have that MCP configured — an **optional external dependency** — otherwise any crawler that reports the rendered meta, headings, canonical and schema for a live URL).

**Owner-blocked post-launch items → `queues/`.** Every post-launch action that only the owner can perform (registry/directory account sign-ups, login-gated pastes, forum or community posts under their identity, syndication approvals) is routed into the stream's `queues/` folder per the SKILL.md owner-action queue rule (backlink-shaped → `queues/backlink-queue.md`, media-shaped → `queues/media-queue.md`, else `queues/manual-queue.md`) — never left as a note inside the build log or a "waiting" line in STATE files. P5.S3 then sweeps for anything missed.

**Write to** `P4-Build.S3-Web.md`: build log — pipeline used, repo/`web/` location, deploy target + live URL, hardening results table, per-page copy-match diff table, wiring-verification evidence (transactional send message ID, analytics test event, `dig` output), documented skips, open placeholders.

**Def-of-success — ALL must pass before Owner sign-off (fail → improvement loop per SKILL.md, never advance):**
- `/critical` run recorded on the shipped surface; the score is advisory (target ≥ 8/10) — the gate is the PASS/FAIL criteria below, not the number.
- Lighthouse mobile **≥ 95** (per `/web-site-creator`'s gate).
- Live copy matches the approved Copy sources section 1:1 — zero builder-invented sentences.
- Keyword contract implemented: page titles, meta descriptions, H1s, and heading hierarchy follow the `P4-Build.S1-Keywords.md` intent-to-page map; `llms.txt` + FAQ answer its AI-search phrasings.
- All hardening rows green or a documented skip with reason.
- Severity-ranked SEO/GEO error table present in the build log; zero High-severity rows open.
- `llms.txt`, JSON-LD, sitemap, RSS feed (`/rss.xml` + autodiscovery `<link>` in every layout), and the agent-discovery endpoint present and reachable.
- `/ai-seo-llms-builder audit` returns **Structure ≥7 and Citability ≥7** on both llms files, with zero HIGH findings open. Reachable is the floor, not the bar: a file can be served, well-formed and still route agents at pages nobody would quote.
- Wiring verified live: one test form submission actually received (message ID in the build log), one analytics test event visible in the project, and `dig` output for SPF/`_dmarc`/DKIM selectors pasted into the build log.
- Exactly ONE root SPF TXT on the domain, matching the merged value recorded at P4.S0 — verified by `dig`, not by intent.
- Every interactive tool / lead-magnet page carries the services-CTA + email-capture pair (Free-tool page rule above), with the capture source distinct from the magnet-delivery patterns; article templates render a services CTA unconditionally.
- The build ran on the declared house stack, or the override is recorded in `P2-Viability.S2-Tooling.md` with its reason.

**Gate out (mandatory — see SKILL.md house rules):**
1. Build complete + hardening table above all green (or documented skips).
2. Invoke `/critical` on the shipped surface — does the live page match the approved Copy sources section of `P4-Build.S2-Copy.md`? Does it overpromise vs `P1-Ideation.S6-Offer.md`? Would the P1.S3 ICP recognize themselves in the hero within 5 seconds?
3. Fix; note what changed.
4. Present the live URL + hardening results + critical findings to the owner. **Wait for their explicit approval. Never auto-advance.**

**Checkpoint:** "Web live at [URL]. Hardening: [results]. Build shipped — next: tear down the top 3 competitors' source to find what they ship that we don't (P4.S4), then the sales deck PDF."

**Next:** `stages/P4-Build.S4-SourceGap.md` — the hardening pass above checked this site against a checklist; P4.S4 checks it against the shipped HTML of the 3 competitors who actually rank, and any gap it finds is fixed back into this build.
