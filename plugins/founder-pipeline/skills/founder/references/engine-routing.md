# Engine + skill routing — the canonical per-step map

This file answers three questions for every one of the 25 steps: **which skills to invoke**, **what to do when a routed capability is not installed**, and **which execution mode to run the step in**. Stage files govern the *what* of each step; this file governs the *how*. On conflict, the stricter gate wins.

**Engine routing is mandatory, not advisory.** The step sequence is always serial and human-gated, but INSIDE a step the execution mode differs, and picking the wrong one wastes either tokens or evidence quality.

**Legend.** **plain** = single-threaded main loop · **fan-out** = parallel research subagents (or a deterministic workflow runner for large sweeps): multi-modal gathering plus adversarial verification of what comes back · **judge panel** = N independent takes scored by parallel judges, synthesise from the winner · **delegated** = one subagent runs a whole sub-pipeline on its own context and returns only its conclusion. Fan-out and judge panels multiply *thoroughness*, never *judgment* — they gather and stress-test evidence; the owner's gate decisions stay human.

## How the "If unavailable" column works

Skills that ship inside this plugin are invoked **namespaced**: `/founder-pipeline:<skill>`. Everything else falls into one of three buckets, and the third column says which:

1. **Optional plugin dependency** (`posthog:*`, `Notion:*`, `cloudflare:*`, `frontend-design:*`) — a public plugin you install separately. Named where it helps; never required.
2. **Optional connector or paid API** (a keyword/backlink data provider, a CRM, a prospect database, a mail or spreadsheet connector, a design MCP) — try the connector, then its REST API with credentials from your secrets store. If neither is reachable, mark the step's tracking criterion `BLOCKED` and add a `queues/manual-queue.md` row to backfill. **Never silently substitute weaker data — a WebFetch guess or a training-data estimate presented as measured data is a FAIL, not a fallback.**
3. **No skill ships for this capability** — run it inline to the shape described. If your own install happens to have a dedicated skill for it, use that instead; the gate is identical either way.

A missing optional dependency is **never** a reason to skip a gate. It is a reason to mark a criterion `BLOCKED` with the exact missing input named.

## Orchestration + model routing

**Orchestration decision (fixed):** the pipeline runs in the **main conversation, sequentially, with your top-tier model as the main loop** — never below the HIGH rung. The main loop IS the orchestrator: no swarm or workflow engine drives the step sequence itself, because the steps are serial and gate-dependent, and parallel orchestration either bypasses a gate or blocks on an unapproved assumption. INSIDE a step, fan-outs run as background subagents per the table above. Reach for a deterministic workflow runner only when a single step's fan-out exceeds roughly 6 parallel agents with deterministic control flow (P3.S1 enrichment at 20+ accounts, P4.S1 SERP sweeps at 10+ clusters).

**What "orchestrate" means here** — the serial gate-sequence is fixed; the research and verification *within* a step is where you go wide:

- **Use multi-agent workflows aggressively.** Default to fanning out, not to doing it single-threaded. If a step involves gathering or checking anything non-trivial, that is a fan-out, not one agent reading one source.
- **Fan out across different sources AND angles.** Not N copies of the same search — each researcher gets a distinct source, segment, competitor or lens, blind to the others, so they surface different things.
- **Adversarially verify every important claim.** Spawn skeptic agents whose ONLY job is to refute the claim, prompted to default to "refuted" when uncertain. A load-bearing claim (a competitor weakness, a volume number, a differentiator, a profit assumption) that has not survived a dedicated refutation attempt is not verified, it is merely unchallenged. Majority-refute → the claim dies or is downgraded to `[assumption — validation: ...]`.
- **Run a completeness critic before calling ANY phase done.** A final agent asks "what is missing — a source not swept, a claim not verified, a segment not covered, a def-of-success criterion not actually tested?" Whatever it finds becomes the next round of work. The phase is not done until the completeness critic comes back empty.
- **Design whatever orchestration shape the work calls for.** The patterns above are a FLOOR, not a ceiling — compose novel harnesses (tournaments, self-repair loops, staged escalation) when a step warrants it. Thoroughness is the goal; token cost is not the constraint. Fan-out and verification multiply *evidence quality*, never *judgment* — the owner's gate decisions (or, in unattended mode, the fresh-context critic's GATE line) stay the authority checkpoint.

**Per-step model tiers (for subagents; the main loop always stays PEAK).** Four rungs, named by tier and never by model codename — codenames age out within months and this floor has to survive them. Map them onto whatever models your install has: **PEAK** = your top-tier reasoning model · **HIGH** = your strong reasoning model at a faster/cheaper setting · **MID** = your default general-purpose model · **CHEAP** = your fastest small model.

| Tier | Steps / roles | What it's for |
|---|---|---|
| **CHEAP** | research-*gathering* fan-out: P1.S3 sizing, P1.S4 data gathering (inside the delegated prediction run), P1.S5 competitor scouts, P1.S7 collision + WHOIS sweeps, P3.S1 per-account enrichment, P4.S1 SERP/trends checks, P5.S3 queue-sweep agents, P1.S1 intake digests | high-volume, verifiable, structured extraction |
| **MID** | synthesis over provided context: drafting inside P1.S2, P1.S6, P2.S1, P2.S2, the P4.S2 format spec, P6.S1, P6.S2, P6.S3; `/founder-pipeline:offers`; the pricing SCORECARD ARITHMETIC only (never the pricing judgment — that is HIGH); routine low-risk stage judges (P2.S2, P4.S1, P6.S2); the P5.S1 launch-item subagents (each carries its own skill's gates); the P4.S4 fix subagent; the P4.S5 deck build | synthesis over provided context |
| **HIGH** | strong-but-not-maximal judgment: `/founder-pipeline:critical` on the money-gate steps P1.S6 and P2.S1; `/founder-pipeline:pricing` tier design, WTP and floor computation; the `/founder-pipeline:marketing-psychology` per-page pass at P4.S2 | strong judgment on money-bearing gates |
| **PEAK** | maximum judgment / adversarial / customer-facing-permanent: BOTH kill-stage passes (P1.S1, P2.S4); the P1.S4 prediction synthesis + verdict; every final verify and completeness critic; every adversarial-refutation agent; the price-ceiling critical pass (P2.S3); customer-facing words that ship — hero, tagline and opener through `/founder-pipeline:brand-voice`, blog drafts through `/founder-pipeline:blog-launch`, every translation pass, the P1.S7 name-selection judge panel and tagline; and the main loop itself | maximum judgment, adversarial reasoning, voice fidelity |

**Two kinds of fan-out, two tiers.** Research-GATHERING fan-out (segment, competitor and SERP sweeps, enrichment, queue sweeps) = CHEAP. Adversarial-VERIFICATION fan-out (refutation critics on load-bearing claims) and the completeness critic = **PEAK**. A weak skeptic rubber-stamps — the refutation and phase-done judges never run below the top rung, and are never down-tiered by the escalation rule.

**The scaffolding rule (what lets a cheaper model deliver top quality — mandatory whenever CHEAP or MID runs):** the prompt MUST carry the structure the model will not supply itself — (1) an explicit output schema (sections, tables, max words); (2) evidence discipline spelled out: a URL per claim, `VERIFIED` vs `ASSUMED` labels, "'not found' is a valid answer", "no invented numbers"; (3) the exact judging / def-of-success criteria **pasted in**, never referenced; (4) one narrow question per agent — a cheap model does one thing well; (5) for judges, the mandatory verdict-block format (`PASS/FAIL per criterion + GATE + CRITICAL SCORE: X/10`). A cheap model with this scaffolding beats an expensive model with a vague prompt; a cheap model without it produces confident garbage — and if the scaffolding cannot be written for a task, the task was never cheap-tier.

**Escalation rule:** a deterministic ladder, CHEAP → MID → HIGH → PEAK. Any CHEAP/MID/HIGH output that a judge fails twice re-runs once on the next rung up, terminating at PEAK — where "failed twice" means the missing ingredient is real-world evidence, not a bigger model. The adversarial and completeness critics (PEAK) are the judges, never the judged, and are exempt from down-tiering. Never economise on: kill passes, final verifies, pricing judgment, customer-facing words.

**Cross-cutting.**
- Mid-run tangent ideas ("we could also build Y") get captured **outside** the stream folder — an ideas file, your task board, a queue row in a different stream — never into the current stream. The focus guard applies to conversations too.
- When resuming a stream that was touched in another terminal, re-read `brief.md` and `PROGRESS.md` before continuing; do not trust the conversation's memory of where things stand.
- Connector-backed tools (a keyword/backlink data provider, a CRM, a prospect database, a spreadsheet connector) degrade gracefully in exactly one direction: connector → that vendor's REST API with credentials from your secrets store → `BLOCKED` on the step's tracking criterion, with a queue row to backfill. Never silently fall back to weaker data and present it as equal.
