## 4.1 Per-page meta

- [ ] [S] `<SEO/>` component sets per page: title, description, canonical, full OG + Twitter set, geo meta, theme-color, hreflang
- [ ] [S] **`<title>` opens with the same words as the `<h1>`, and lands in 30-60 chars.** Google rewrote **76% of titles** in Q1 2025 (up from 61%); title/H1 agreement drops the rewrite rate to **20.6%**, and 84.87% of titles Google leaves ALONE sit in the 30-60 band [Zyppy, 80,959 URLs]. Brand goes last or is dropped. This is the strongest single quantified on-page effect in the whole pipeline and it is a mechanical pass, so do it before anything glamorous.
- [ ] [S] **Measure agreement on the OPENING WORDS, in sequence — never as bag-of-words overlap.** What Google keys on is where the title *starts*, so the check is: the first 3 words of the title equal the first 3 words of the H1 (or all of them, if either is shorter). Do not filter stopwords out before comparing — "An" / "The" / "of" are part of the literal opening. A set-overlap ratio measures the wrong thing in both directions: it fails a tight keyword-led title under a longer conversational H1 (a real `/mentor/` page scored 0.29 on set-overlap while opening word-for-word on its H1 — *"An engineering mentor…"*), and it passes a title that shares many words with the H1 but opens on the brand name, which is the actual mistake. **Never pad a title with filler lifted from the H1 to raise a ratio** — worse for the reader, and it does nothing to the rewrite rate. If you run an automated title/H1 check anywhere, re-implement it as a prefix comparison to match.
- [ ] [S] **When the content's own title is too long to fit any suffix, add a hand-written short form in frontmatter** (`seoTitle` or equivalent) holding a PREFIX CUT of the real title, so the opening still matches, and let the template fall back to the full title when the field is absent. Long-form titles (blog posts, event and talk names) routinely run 45-75 chars before a brand suffix adds 16-32 more, so keeping the full title *and* landing under 60 is arithmetically impossible. Mechanical truncation is not the answer — it produces amputations ("Boost Your Team's Efficiency with a Powerful") that Google rewrites anyway. Let the CUT be editorial and the LENGTH POLICY mechanical: a suffix cascade that takes the richest suffix that fits, then a shorter one, then the bare title. Self-healing, and pages already in band come out byte-identical.
- [ ] [S] **Write `&` as a literal in title props, not `&amp;`.** Template engines escape it again, so the browser tab renders "Hire, educate &amp; impress". Grep title props for `&amp;` before deploy.
  **The failure mode is templated titles that lead with a counter instead of the topic** — one real build shipped `#37 Meetup | <talk title> | <community name>` at 100-118 chars across 31 event pages, spending the most valuable position on a string nobody searches and pushing the actual topic past truncation. Fixed to `<talk title> | Meetup #37`. Audit mechanically:
  ```bash
  # from dist/: how much of each H1 survives in its <title>, and how long the titles run
  python3 - <<'EOF'
  import re,glob,html
  for f in sorted(glob.glob('**/index.html',recursive=True)):
      h=open(f,encoding='utf-8',errors='ignore').read()
      t=re.search(r'<title>(.*?)</title>',h,re.S); h1=re.search(r'<h1[^>]*>(.*?)</h1>',h,re.S)
      if not t or not h1: continue
      cl=lambda m: html.unescape(re.sub(r'\s+',' ',re.sub(r'<[^>]+>','',m.group(1)))).strip()
      T,H=cl(t),cl(h1)
      tw={w.lower().strip('.,:?!') for w in T.split() if len(w)>3}
      hw={w.lower().strip('.,:?!') for w in H.split() if len(w)>3}
      ov=len(hw&tw)/len(hw) if hw else 0
      if ov<0.5 or len(T)>70: print(f"{ov:4.0%} {len(T):4} {f}")
  EOF
  ```

## 4.2 Structured data

**Schema earns rich results and entity resolution, never rankings or AI citations — say so, don't oversell it.** [Mueller, Apr 2025, verbatim: *"Structured data won't make your site rank better."*] The only controlled experiment on record (Ahrefs, 1,885 pages with JSON-LD added vs ~4,000 matched controls, difference-in-differences) found no significant lift on AIO/AI Mode/ChatGPT and a **−4.6%** move on AI Overviews; a 5-engine live-retrieval test (searchVIU) found all five **ignored JSON-LD** entirely. Mark up for the rich result or the entity graph, never for a ranking or citation bet.

- [ ] [S] **Eight types, no more:** `Organization`+`WebSite` site-wide (`logo` + `sameAs` array identical to the brand's canonical profile set everywhere), `BreadcrumbList` on posts and deep pages, `Article`/`BlogPosting` with `author` → `Person` `@id` on posts, `ProfilePage`+`Person` on the bio/about page, `Event` **in-person only** (online-only events don't qualify for the rich result — Google's own restriction), `FAQPage` on any page carrying a **visible** FAQ accordion, **`HowTo` on any page carrying visible numbered steps**, and **`Speakable`** where a page has a clean spoken-answer section. `Service`+`OfferCatalog` and standalone `WebSite`-as-a-type stay cut: no live rich result, no purpose (SiteLinks Searchbox was retired).
- [ ] [S] **`HowTo` and `Speakable` ship by standing decision — same terms as `FAQPage`.** This line previously read "exactly six types … `HowTo` stays dead (retired Sept 2023)". That rule is withdrawn: the standing decision that un-banned `FAQPage` was extended to cover both types. Evidence and reasoning live in `references/metadata.md` §8.4 and `${CLAUDE_PLUGIN_ROOT}/skills/ai-seo/references/aeo-patterns.md` §8. The evidence itself did not change and is not in dispute — `HowTo`'s rich result was retired in 2023 and `Speakable` has no rich result in this market — so **implement them, forecast nothing from them, and do not reopen the argument.** The mirroring constraint below is the enforceable part, and it applies to all three: a node whose content the reader cannot see is still a defect.
- [ ] [S] **`FAQPage`, `HowTo` and `Speakable` mirror visible content 1:1 — never carry a question, step or sentence the reader can't see.** In the mandate by standing decision, not on evidence: the FAQ rich result was killed 7 May 2026, and schema-only facts were read by **0 of 5** engines [searchVIU, Oct 2025] and never used across 319 prompts [Otterly.ai, Dec 2025–Mar 2026]. Evidence and reasoning: `references/metadata.md` §8.4 — settled, don't reopen. The mirroring constraint is the enforceable part, and it is the one thing here worth machine-checking: fail a page whose schema answers appear nowhere in the DOM
- [ ] [S] **If the brand runs recurring real-world events, `Event` is the highest-value type available to it** — a fully-supported rich result with its own SERP surface plus Google Events, renewed every time you run one. A community doing 12 meetups a year across 4 cities is a recurring rich-result feed most niches leave completely unclaimed. In-person only; needs `name`, `startDate`, `location`, `organizer` (→ the Organization `@id`), `eventAttendanceMode`, and `offers` if ticketed. Emit it for PAST events too — the archive is what ranks between editions.
- [ ] [S] **Cross-domain entity graph when the owner runs several properties.** One `@id` per real entity, referenced across domains rather than restated: `Person` (personal site) ←`founder`/`worksFor`→ `Organization` (community site) →`organizer`→ `Event` (conference site). Give the Person a `sameAs` cluster (LinkedIn, X, YouTube, Crunchbase, speaker profiles, Medium/Substack) and, if genuinely notable, a **Wikidata item** — Wikidata is the documented Knowledge-Graph feed and the realistic path to a Person knowledge panel. This is the one metadata item that compounds into BOTH blue links and AI answers, because entity popularity measurably raises LLM factual accuracy about you [Mallen et al., ACL 2023, peer-reviewed: accuracy rises monotonically with entity popularity]. Everything else in 4.2 is rich-results-only.
- [ ] [S] **No hardcoded fallbacks in shared schema components** (a default `price` publishes a fake price site-wide); omit `Offer` entirely when pricing is private
- [ ] [S] Prices in copy = prices in `Offer` schema — text-only prices are invisible to rich results
- [ ] [S] **Date shown visibly on-page; `dateModified` emitted only on a genuine content change, never automated.** Not the AI-citation lever it was once framed as — SearchPilot's own A/B on adding `dateModified` schema was **inconclusive**, and Mueller (Apr 2025) called date-bumping "just lazy"; Illyes goes further — omit `lastmod` rather than emit an unreliable date, because an inaccurate date makes Google distrust **the whole site's** dates, not just the one page
- [ ] [S] Review stars: `AggregateRating` only on an eligible **`Product`** type (never LocalBusiness/Organization/Service — self-serving is ineligible); render VISIBLE stars; honest `ratingCount` vs `reviewCount`; purge any site-wide `aggregateRating`. Full recipe: `${CLAUDE_PLUGIN_ROOT}/skills/seo-audit/references/review-stars-rich-snippets.md`
