# P5.S1 — Launch: ship the distribution assets → `P5-Activation.S1-Launch.md` + `P5-Activation.S1-Launch/`

**Phase: P5-Activation**

**Routing:** fan-out (one subagent per launch item) · launch items MID, blog drafts PEAK · gate critic at the step tier

**Earns its keep** in every stream with a web surface or content motion — this is the step that was structurally missing: the pipeline used to end at "built and queued", and distribution work died in owner-gated queues. Launch is EXECUTION — assets published, servers registered, posts live — not planning. **Performative when** the stream is deck-only with no web/content motion — record the skip in `brief.md`.

**Why post-web, pre-GTM:** GTM (P6.S1) locks channels from observed data. Launch creates that data: which posts get read, which registries send traffic, which magnet converts. Launching after GTM would mean locking channels blind.

## Launch items (fan out in parallel — each item is its own delegated subagent; the step file is the gate-carrier)

1. **First blog posts** — the first 2-3 posts from the keyword contract's intent-to-page map (P4.S1) via `/blog-launch` (full pipeline: draft gate, images, secondary-language mirror if the stream runs one, deploy, syndication, announce). Your top-tier model floor applies. Posts that need the owner's personal story go to `queues/media-queue.md` instead of blocking the launch.
2. **MCP server publication** — if P4.S3 scaffolded an MCP endpoint (or the GTM candidate scored it in): take it end-to-end — implement the remaining tools, deploy, publish the repo, and register in the registries that still accept submissions (see the reality check below). *(The original pipeline routed this to a dedicated MCP-launch skill; that skill does not ship in this plugin. 2a and 2b below carry everything it enforced — do the work inline, or use your own equivalent skill if you have one installed.)* No real question the ICP asks an AI = no server — don't build a toy; record the skip.

   **2a. Build it to score BEFORE the first publish.** Registries grade servers and show the score publicly; a low score is a live trust signal against the stream. Every one of these is cheap at build time and annoying to retrofit (measured on one real server: it shipped at 74/100, and five fixes took it to 98):
   - **`outputSchema` on every tool, plus matching `structuredContent` in every response.** Highest-weighted single item. Declare one shared output schema (`report` prose + `source` URL) and add optional typed fields (`totalScore`, `level`, `benchmarkAmount`, `verdict`) that only the computing tools populate — one schema then serves every tool and still validates. `structuredContent` is additive, so text-only clients are unaffected, but it MUST always be present and match the schema or strict clients reject the response.
   - **The FULL annotation set on every tool**, not just `readOnlyHint`. `readOnlyHint` alone scores zero. Ship `{ readOnlyHint, destructiveHint, idempotentHint, openWorldHint }` — for a read-only data server that is `true/false/true/false`. Define it once as a `READ_ONLY` const and spread it.
   - **Server icon.** Square, ≤1MB, PNG/JPG/GIF/SVG/WebP. The stream's `favicon-192x192.webp` works. Worth a flat 8 points and it is a two-minute upload — but the upload is a native file picker, so an agent must use a browser file-upload tool against the file input's ref, never a click.
   - **Tool naming — read the registry's own tooltip before assuming a convention.** Smithery's rule (from its in-UI tooltip, mid-2026) is: *"Tool and trigger names should form a navigable tree via dot-notation (e.g. `admin.tools.list`). Flat lists and over-nested paths both reduce the score."* A consistent `verb_object` snake_case set scores **zero** here — that was tested on a live server and did not move the number. **But do not adopt dot-notation reflexively:** the Anthropic Messages API restricts tool names to `^[a-zA-Z0-9_-]{1,64}$`, so dotted names break Claude as a client. When the stream's primary consumer is Claude, take the naming penalty and record the reason — a working integration beats a registry point. Decide this at design time; renaming a published tool is a breaking change to a public interface.
   - **Description, homepage, display name, and a config schema** (even an empty one for a no-auth server) — all separately scored.

   **2b. Registry reality check — verify before submitting, the ecosystem churns fast.** Any registry list older than ~1 month is stale. Per registry, in this order: (i) search the registry for the server first — many now **auto-ingest from the Official MCP Registry**, so publishing there once may be the only action needed (PulseMCP removed its submission form entirely and ingests daily / processes weekly; LobeHub auto-listed within a day); (ii) confirm the submission URL still resolves — stale paths 404 (`lobehub.com/mcp/submit`) and whole sites pivot (`cursor.directory/mcp` became a Cursor *plugin* directory); (iii) when checking whether a listing exists, **confirm the namespace** — a 404 on a guessed namespace is not evidence of a missing listing, and an SPA shell returns HTTP 200 while rendering "not found".
   - **The Website/Homepage/URL field must be the stream's own URL, never the GitHub repo.** GitHub `nofollow`s every outbound link, so a repo-pointed listing passes zero equity. Where a form offers only one free-text URL, that URL is the stream's.
   - **Docker `docker/mcp-registry` was a dead end as of mid-2026** — 730 open PRs, last community server addition merged months earlier, everything since `chore: update pin` bots. Re-check before you spend time on it; if it still looks dormant, open the PR as a free option, mark it `parked`, don't track it.
   - **Republish after every server deploy.** The score is computed at publish time, not continuously: a deploy that adds tools or schemas changes nothing on the listing until you publish again.
3. **AI skill publication** — if the stream's method/framework works as a public skill: publish it — public repo plus the skill marketplaces and awesome-lists that accept submissions. *(A dedicated skill-publication skill does not ship in this plugin; do it inline, or use your own if installed.)* Same bar: real recurring use, or skip with reason.
4. **Lead-magnet distribution** — the magnet shipped at P4.S3 gets its distribution: announce post, community shares (queued where owner-gated), and its capture events verified live in your product-analytics tool (PostHog in the P1.S1 house stack).
5. **Day-0 baseline snapshot** — ONE rank/citation baseline for the keyword contract (a rank API's `ranked_keywords` call + an AI-mention probe), stored in the step folder. `references/dataforseo-playbook.md` covers the DataForSEO version of this read; the API is an optional third-party dependency, and any rank source works as long as the same source is reused for every later comparison. This is the single day-0 snapshot; P6.S2 owns all recurring reads. AI-mention probes vary run to run (in one run the same prompt set read 0 of 4 and 2 of 23 citations on the same day) — probe each prompt on ≥ 2 engines, and treat a citation as baseline only if it repeats; a one-off hit is logged as "unstable". DataForSEO's `ranked_keywords` rejects a filter on the keyword field — for a fixed keyword list, use a live SERP at depth 100 per keyword instead.
6. **Indexation + engines** — run **`/web-indexation`**: one-time per-property setup (Search Console, Bing Webmaster, IndexNow key, plus your home market's non-Google engine if it has one) plus the every-deploy steps (IndexNow ping, reindex queue — never direct Search Console clicks) for every page shipped at launch.
7. **Local Business identity** — only if the stream has a local/service-area component (in-person, region-bound, or a founder-as-consultant brand courting local + AI-Overviews visibility); skip with reason if the stream is pure global/online. Build the business profile out fully on the map/local platform your market uses — category, service area, products/services section, hours, photos, Q&A. NAP (name, address or service area, phone) must be **identical** across the site's JSON-LD, the business profile, and every directory. Then get ≥1 territory-appropriate local directory citation live: in a Google-dominant market that is the main local directories; in a market with a strong non-Google engine it is that engine's directory plus its webmaster tools (Czech/Slovak worked example: Firmy.cz + Seznam Webmaster).
8. **Sanitization gate for anything published out of internal repos** (open-sourced skills/plugins/MCP code, playbooks turned into posts, screenshots) — run the `ASSET-AUDIT.md` grep from P1.S1 over the export directory; it must return nothing. Respect the audit's freeze windows for deploys.

*(The original pipeline had an umbrella "web activation" skill covering items 4, 5 and 7 for a site that just shipped via `/web-site-creator`. It does not ship here — run the three items directly as written above. Item 6 routes to `/web-indexation`, which is its own standalone skill, invoked independently at every future deploy too, not just here.)*

**Owner-gated items** (community posts under the owner's identity, account sign-ups, syndication approvals) go to the queues per the SKILL.md hard rule — but the launch step DOES everything that doesn't require their identity. The test: at gate time, "waiting on the owner" items are queue rows; everything else is DONE.

**Skills:** `/blog-launch`, `/web-indexation`, `/web-backlinks` (only to hand over — link building is P5.S2), `/brand-voice` (all reader-facing copy, top-tier model). MCP-server and public-skill publication run inline per items 2–3.

**Write to** `P5-Activation.S1-Launch.md`: launch-item table (item | status DONE/QUEUED/SKIPPED+reason | evidence URL | first-signal metric), day-0 baseline location, INDEX of the step folder (submission logs, published URLs).

**Def-of-success — ALL must pass before owner sign-off (fail → improvement loop per SKILL.md, never advance):**
- `/critical` run recorded; the score is advisory — the gate is the criteria below.
- ≥ 2 blog posts LIVE (URLs returning 200), from the keyword contract. Hard floor: ≥1 post LIVE; between 1 and 2, proceed only via the SKILL.md override mechanism recorded in this file with the owner's explicit sign-off; 0 live posts = FAIL, no override path.
- MCP and skill items each either SHIPPED or SKIPPED with the "no real question / no recurring use" reason — never silently absent; every evidence URL in the launch-item table (posts, registries, repos) fetched and returning 200 at gate time; fetch log stored in the step folder.
- If an MCP server SHIPPED: its registry **quality score is ≥ 90**, with the per-criterion breakdown pasted into the step file. A criterion may be deliberately forfeited only with the tradeoff written down (e.g. flat tool names to stay Claude-compatible) — an unexplained miss is a FAIL. Below 90 = FAIL, fix and republish — the score is public and reads as a competence signal on the stream. Verify the live server independently of the listing: `tools/list` shows `outputSchema` and a 4-key `annotations` object on every tool, and one real `tools/call` returns `structuredContent` matching the schema. A listing claiming N tools while `tools/list` returns N+1 means the listing is stale — republish, don't edit the listing by hand.
- Lead magnet distributed: announce-post URL recorded (fetched, 200) AND ≥1 capture event visible in the product-analytics tool (event name + timestamp logged in step folder) — both UNCONDITIONAL. Owner-identity shares may land as queue rows with ready artifact paths; the announce post and capture verification never queue.
- Zero "drafted, awaiting" items outside the queues; every queued row has the ready artifact path.
- Day-0 baseline snapshot exists; indexation requests queued via the shared reindex queue (no direct Search Console clicks).
- Sanitization grep output (empty) pasted into the step file for every artifact published from an internal repo, or "no internal-repo publications" recorded.
- Local Business identity: EITHER shipped (business profile live + NAP matched across site/profile/directories + ≥1 directory citation live, all evidence URLs fetched 200) OR SKIPPED with the "no local/service-area component" reason recorded — never silently absent.

**Gate out (mandatory — see SKILL.md house rules):**
1. Draft `P5-Activation.S1-Launch.md` as items complete.
2. Before invoking `/critical`, the gate-carrier re-fetches every evidence URL itself — a subagent's self-reported DONE is not evidence.
3. Invoke `/critical` — attack the DONE column hardest: is each item verifiably live (URL, registry listing, event in the analytics tool), or "done" meaning "written"?
4. Revise; note what changed.
5. Present to the owner. **Wait for their explicit approval. Never auto-advance.**

**Checkpoint:** "Launched: [N] posts, MCP [shipped/skipped], skill [shipped/skipped], magnet distributed, local identity [shipped/skipped]. [M] items in queues for you. Links next — backlinks + internal mesh."
