# Web Creator — Changelog

Part of the /founder-pipeline:web-site-creator reference set. Split from an earlier monolithic build reference (v16). Headings keep their original § numbers.

Entries are kept because each one records a rule and the failure that produced it. Site names in the
war stories are anonymised: `example.com` and `example.org` stand for two different sites built on the
same stack, and `example.net` for a third.

- **§14.5.11 first-touch attribution vs Safari ITP.** The §14.5.8 rewrite-on-pageload trick is correct for consent and wrong for attribution: it makes the cookie expire after 7 days of *absence*, so a considered purchase (read → wait 3 weeks → book) converts as `direct` and organic search silently loses the credit. Fix is a server-set HttpOnly first-touch mirror (`POST /api/attr`), write-once server-side, durable copy wins on read. Footgun flagged: it must stay a POST on a cache-excluded path — a cached `Set-Cookie` leaks one visitor's attribution to every later visitor. Phase 6 checklist item added.

## Skill restructure

- v4.1: **Two launch-time instrumentation bugs promoted to blockers, both found live on sites this skill had already launched.** Triggered by a product-analytics question on one site that turned into an audit.
  1. **New §6.3a + `launch.md` §14.5.9 — canonical host.** A zone answering 200 on BOTH apex and `www` splits cookies per host, so the same person counts twice and the second visit arrives **self-referred** — the site as its own top referring domain. It also splits link equity, and it is invisible: both hosts render, the canonical tag is usually right, nothing 404s, nothing fails a build. A sweep of every live zone in one estate found it on **three** sites, launched months apart. Recorded with it: read the direction off `<link rel="canonical">` rather than assuming `www` (one of the three was canonical on the **apex**, so its rule ran the other way); fix with a zone-level **Redirect Rule**, because a static-assets redirects file lives in the assets layer that a worker-first route or an edge cache skips; carve out `/mcp*`, `/api/` and `*.txt` verification files, since a 301 on POST is not reliably followed and verification fetchers do not all follow redirects; append the host rule **last** so narrower path rules still resolve in one hop; and wait ~30s before believing a negative, because a deep path still answering 200 straight after the API call is propagation, not a broken expression — that one nearly sent the audit debugging a correct rule.
  2. **New `launch.md` §14.5.10 — analytics load timing.** A perf pass will push analytics behind `requestIdleCallback` or a first-interaction listener. Doing that to the product-analytics SDK destroys attribution, because `pointerdown` is the event that *precedes* a click: on a landing page the dynamic import races the navigation and loses, the **entry pageview is never sent**, and the SDK's first sight of the visitor is page two — whose referrer is the site itself. Measured on one affected site: 675 self-referred people, **666 (98.7%) with no earlier tracked pageview at all**, i.e. ~34% of visitors whose real source (Google, LinkedIn, ChatGPT) was discarded and relabelled Referral. The same query on a healthy site returns 123 / 18 (15%) — ordinary returning visitors — so the **ratio is the diagnosis**, not the raw self-referral count; the query is in §14.5.10. Ship the split instead: product analytics eager (the session recorder still deferred, which is where the Lighthouse cost actually was), tag-manager and ad pixels lazy, and a comment at the call site or the next perf pass silently undoes it. Also folded in: guard dev traffic on `location.hostname`, not a build-time dev flag — preview and local-dev servers both serve production builds, and `localhost` had climbed to one site's **6th-largest referring domain**.
  Touched: `phases/6-launch.md` (new §6.3a, two §6.2 items), `references/launch.md` (new §14.5.9, §14.5.10), `references/gates.md` Appendix F.
- v4.0: **Consent model inverted — reject-only is now the default, and the skill gained an actual recipe instead of a one-paragraph stance.** Triggered by the owner asking whether one site needed a consent-management platform. The audit found the gap was worse than a missing banner: that site ran product analytics with autocapture, session recording and cookie persistence plus eight 90-day attribution cookies on first paint, while its privacy policy promised a cookie bar in four separate places and named a since-retired hosting processor without naming the analytics vendor at all. A second site had the mirror problem, cookieless by design with both policies stating "there is nothing to consent to". The owner chose opt-out (Reject + Accept, no Settings, accepted by default) for both, and made it the skill default.
  1. **New `references/launch.md` §14.5.8** — the full recipe. `consent_v1` cookie contract (versioned name so a policy change invalidates every stored answer in one line; cookie not localStorage because localStorage throws in private-mode Safari and this is the one script that must not fail open). The `html[data-consent]` + CSS-reveal pattern is forced by the stack: HTML is CDN-cached and identical for every visitor, so the bar can't be server-rendered conditionally and a Worker that varies it would make every page uncacheable. Bonus nobody designed for — the attribute is JS-only, so no-JS visitors and non-executing crawlers (Googlebot, GPTBot, ClaudeBot, PerplexityBot) never see the bar and it can't pollute an LLM's reading of the page. Pull `window.__consent` for init-time config (an event that already fired is invisible to a later listener), push a CustomEvent for live changes (a bundled analytics module and an inline bar script share nothing but `window`).
  2. **Six silent failure modes documented, five of which ship looking correct.** `opt_out_capturing()` stops *all* capture including pageviews unless `cookieless_mode: 'on_reject'` is set at init — the obvious API for "downgrade but keep counting" does the opposite and nobody notices for months. PostHog's `cross_subdomain_cookie` defaults true so `ph_<token>_posthog` lives on `.example.com`; a host-only `max-age=0` delete leaves it untouched, which is the #1 way this feature ships broken. `reset()` alone mints a new id against the unchanged backend and writes a *fresh* cookie. `pointerdown` fires before `click`, so any interaction-gated analytics loader boots, awaits its import, and inits at full config *after* the visitor rejected. Guard on `posthog.__loaded`, not `window.posthog` — the CDN snippet leaves a stub array that queues calls and replays them with the wrong intent. And where recording is started by hand for perf, `disable_session_recording: true` at init means "set it on reject" is a no-op.
  3. **Consent Mode v2 flipped to granted-by-default, with `region` and `wait_for_update` DELETED rather than flipped.** Flipping the seven signals while leaving `region: [27 EEA codes]` grants the rest of the world and denies Europe — the exact inverse of the decision, and an easy thing to leave behind in a hurry. `wait_for_update: 500` adds 500ms to every hit waiting for an update that never comes once the state is known synchronously. Emit a *denied default* for a stored rejection rather than granted-then-update, or a `gcs=G111` hit occasionally leaks before the correction lands. Also fixed a pre-existing anti-pattern: `security_storage: 'denied'` covers anti-fraud and authentication and should be granted in both payloads.
  4. **The legal divergence is stated once and made reversible.** Czech law has required opt-in since 1 Jan 2022 (374/2021 Sb. amending §89(3) of 127/2005 Sb.). §14.5.8 names the two constants that switch back to strict opt-in and requires it for client builds, EU-regulated sites, and anything running Google Ads to EEA/UK traffic — Google's EU User Consent Policy needs a `granted` signal to reflect real consent, and Google is a live enforcer where the regulator is theoretical.
  5. **The privacy page is called the enforceable half** (Art. 13 GDPR), with a ship-the-policy-first instruction if time is short: cookie table incl. the strictly-necessary Cloudflare cookies (without them the first person to open DevTools after Reject reports the bar as broken), a `#cookie-settings` section, every processor named, Cloudflare Web Analytics named as out of the bar's scope since it's edge-injected and ungovernable from the repo, and a bumped date.
  6. **Corrected same-day from a live build, which disproved this skill's own first draft.** The Reject recipe originally shipped here (`stopSessionRecording` -> `set_config({persistence:'memory'})` -> `reset(true)` -> sweep) does NOT work. Measured against `array.js` 1.417.1 in a browser: `persistence:'memory'` at init still writes `ph_<token>_posthog`; `set_config` cannot swap a backend fixed at construction and the cookie reappears seconds after deletion; `opt_out_capturing()` stops capture but still writes the cookie; `cookieless_mode:'on_reject'` + opt-out made `is_capturing()` return false, killing the pageviews the design existed to keep; sweeping at 0s/3s/8s/pagehide was undone every time. **The only mechanism that holds is not loading the library**, which also cannot break when the vendor ships a new bundle. Consequence recorded in the skill: "Reject keeps anonymous pageviews" is not achievable this way, so that trade-off has to be agreed BEFORE the privacy copy is written. Also recorded: the measurement trap that produced several false "clean" readings — clearing storage on a page where PostHog is still live lets it rewrite the cookie before navigation, so always clear on a page where the library cannot run.
  7. **Visual default + the mobile dead end.** Thin ~50px stripe, actions as underlined text links that stay `<button>` elements, ~50% background with `backdrop-filter` on a `::before`, policy link in body text colour not the brand accent, dismiss-on-scroll that records nothing, ~6px vertical padding so text links clear WCAG 2.5.8's 24px target minimum, and reserved height driven by a ResizeObserver rather than per-breakpoint literals (a hardcoded guess was 18px short at 402px). Plus the trap that nearly shipped: hiding the bar on mobile made the privacy page's "Change your choice" control inert, because it only re-showed a `display:none` bar — a phone visitor had no way to reject at all. The privacy page needs REAL accept/reject controls with a document-delegated handler, and then the reopen concept is unnecessary.
  Touched: `references/launch.md` (§14.5 consent paragraph rewritten, §14.5.1 Consent Mode bullet, new §14.5.8, publish-gate line), `references/gates.md` Appendix F, `phases/3-interactivity.md` §3.2, `phases/6-launch.md` §6.2, `SKILL.md` cheat sheet.
- v3.9: **New §5.4 AI-citation content must-haves, and `FAQPage` reversed from banned to mandated by standing decision.** Triggered by the owner asking for three AI-citation must-haves for a single page build (real numbers in the first 60 words, a data table, FAQ schema + accordion). Three parallel evidence sweeps came back and materially changed two of the three:
  1. **"Numbers in the first 60 words" demoted to a checklist item.** No study has ever manipulated within-page placement of statistics. The "44.2% of citations come from the first 30% of the page" figure [Indig/Growth Memo, 18,012 verified ChatGPT citations] measures where cited text was *found*, not causation — and the same study found 53% of citations came from mid-paragraph. On statistics-anywhere the three benchmarks disagree in SIGN: Princeton GEO +34% PAWC (simulated GPT-3.5 engine) vs C-SEO Bench **−0.53 ranking positions, significantly negative** vs CC-GSEO-Bench +2.4% with trustworthiness falling.
  2. **Data tables kept, but re-justified.** Their ~+20% organic-traffic effect [SearchPilot] stands and is still the largest controlled effect of 2025. As an *AI-citation* tactic they're folklore: the only controlled formatting test — Vishwakarma et al., SIGIR 2026, **252,000 counterbalanced trials across 6 LLMs, 18 factors** — put content structure at **OR 0.79–1.68** and concluded verbatim *"formatting choices had no impact."* The circulating table multipliers (2.5×/4.2×/25.7%/47%) are vendor posts with no methodology, disagreeing by a factor of ten.
  3. **What the sweep added instead — the actual gatekeepers, all absent from this skill.** The same 252k-trial study found four factors at **OR >>10,000, unanimous across all six models**: topic match, retrieval position, **explicit price/cost**, and **recency**. Plus missing-specifications at OR 8.63–243. Visible date, real price number and concrete specifics are now Tier A and **gated at GATE 5**; hedged-language avoidance, self-contained sections and source attribution are Tier B checklist items.
  Also recorded: the section-level counter-rule that body-only GEO rewrites *cut* post-rerank top-10 presence by **16%** [SAGEO Arena], the off-page asymmetry (Trustpilot presence swings citation rate 1% → 53.5% [Seer, 804,491 responses]; branded mentions r=0.664 vs backlinks 0.218 [Ahrefs, 75,000 brands]; **no published correlation coefficient exists for any on-page formatting element**), and a **rejected-claims list** naming three fabricated statistics traced to no primary source — a non-existent "Princeton + Moz, 500,000 URLs, WWW 2026, FAQ schema 3.2×" study, "SE Ranking: data-rich pages get 93% more citations" (absent from the SE Ranking primary), and "schema markup → 2.1× more citations".
- v3.9: **`FAQPage` un-banned — schema mandate 5 types → 6.** This reverses v3.5/v3.6 and it is a **standing policy decision by the owner, not an evidence update**. The evidence went the other way and got stronger: the rich result is still dead (killed 7 May 2026), the Ahrefs DiD still shows **−4.6% on AI Overviews**, and two new direct tests confirmed engines never read schema-only content — searchVIU (Oct 2025, 5 engines × 8 scenarios) found a JSON-LD-only fact picked up by **0 of 5** systems, and Otterly.ai planted a fact existing nowhere except in FAQ schema and tracked 319 prompts Dec 2025–Mar 2026 with **no platform ever using it**. The owner was shown all of this and chose to ship the markup anyway. **Do not re-derive the removal rule from the evidence — that argument is settled.** If your own house rules go the other way, record that as your decision and move on; the mechanism below is what matters either way. One constraint carried over from the old ban and is now the enforceable part: `FAQPage` is emitted **only** where a visible accordion exists, mirroring it 1:1, because schema-only Q&A is unreadable to every engine tested and is how content silently dies (a live-site audit found a page whose only copy of two Q&As lived inside the JSON-LD). The monthly health script flips accordingly — it no longer flags `FAQPage` as dead schema, it now flags `FAQPage` *without* a visible accordion. `HowTo` stays dead and stays remove-if-present. Touched: `references/metadata.md` §8.4, `references/seo.md` §8.11 + AI-citation levers + health-audit script, `phases/4-metadata.md`, `references/gates.md`.
- v3.8: **Markdown twins (`<route>.md`) added as a Z1 crawler surface, and content negotiation explicitly ruled OUT on this stack.** Triggered by evaluating an edge provider's "Markdown for Agents" feature on two sites: both zones were on the free plan, the converter reported itself non-editable, and the edge feature would have cost a per-zone plan upgrade on every site. Built the free half instead — a post-build HTML→Markdown generator script, a `rel="alternate" type="text/markdown"` link in the layout head, an `llms.txt` stanza, and a `/md-sitemap.txt` index. Measured 87% byte reduction on one site (227 twins) and 91% on the other (84 twins). Four things this taught the skill:
  1. **The `.md` URL is the mechanism, not the `Accept` header.** Buytaert's month of Cloudflare logs: zero crawlers negotiated, every markdown fetch came through a `.md` URL discovered via `rel="alternate"`. suganthan.com's 44 days logged 1,421 negotiated requests but all from live agent tooling, not the named training crawlers. Build the URL; the header is optional.
  2. **Negotiation on Astro + Workers static assets is a trap with a measured failure mode.** Astro middleware never runs for prerendered pages, so it needs a worker-first route over `/*`, which bypasses the asset routing layer — and the static `_redirects` file is evaluated THERE. Verified locally: all 102 of one site's redirect rules silently returned 200 instead of 301. Scoping around it is impossible — the worker-first route list is hard-capped at 100 rules and the site needed 228. Reverted; the wrapper was deleted rather than parked, with the war story left as a comment in the runtime config of both repos so nobody rediscovers it by shipping it.
  3. **Three twin-specific safety rules, each a bug before it was a rule:** twins never enter the sitemap; never emit one for a `noindex`/private route (an unprotected copy at a URL the site's existing noindex layers don't cover — one site's private intake route had four such layers and none would have covered a `.md`); and never set `X-Robots-Tag: noindex` on `/*.md`, which would tell OAI-SearchBot to drop the very content the file exists to expose.
  4. **`llms-full.txt` gets a byte budget once twins exist.** One site's had grown to 956 KB of inlined post bodies — now a duplicate of content one fetch away. Capped at 150 KB of newest-first bodies plus an indexed tail carrying each post's Markdown URL: 956 KB → 184 KB, nothing lost.
  Rule lines in `phases/5-seo.md` §5.2 + GATE 5; full recipe, generator shape and the two conversion defects worth fixing in any port (jammed multi-span headings, label-less icon links) in `references/seo.md` § "Markdown for agents".
- v3.7: **Scope narrowed to brand-new site/repo builds only.** This skill covers a new domain, a new deploy pipeline and all 6 phases. Adding a section or a set of pages to an *existing* repo is a materially lighter job — content/imagery rules, design-system compliance, metadata, on-page SEO, deploy and reindex, with no scaffold, no brand-kit extraction, no site-wide Z1 surfaces and no DNS/zone setup — and running the full pipeline for it wastes a day. If you do that often, split it into your own lighter pipeline that reads this skill's `references/` for the recipes rather than duplicating them. Also added Phase 6.2 / `references/launch.md` §14.5.5 **zone hardening** (Always Use HTTPS, HSTS, TLS min 1.2, Early Hints) as a launch-gate item — a live-zone audit found all four missing on a free-plan zone that had been live for months. Edge-provider web analytics was already on via automatic setup and needed no code change.
- v3.6: **New "live-site health re-audit" mode, because the rules were already here and the site broke them anyway.** Root cause: a health audit of one live site found 18 pages emitting dead `FAQPage` schema (plus a `HowTo` on a 19th), 50 of 67 pages failing the title/H1 rule, and ~45 pages whose header language switcher linked to a secondary-locale URL that 404s. Every one of those rules was ALREADY written in this skill — v3.5 cut `FAQPage` from the mandate, `phases/4-metadata.md` mandates the title↔H1 opening-word match, and `references/seo.md` §8.14 literally warned "set the alternate flag to false on pages without a mirror or the LangSwitcher 404s". The gap was never knowledge; it was that this skill is a BUILD pipeline whose rules are pre-publish checkboxes, and nothing re-runs them against a site that shipped months ago. Five fixes:
  1. **New `references/seo.md` § "Live-site health re-audit"** — the first entry point in this skill for "this site went live a while ago, what has rotted?". Three runnable scripts against the production sitemap (dead-schema detection, title↔H1 + length sweep, locale-mirror 404 loop), following the precedent set by §8.11's OG-image coverage script. Each prints offending URLs, so the output IS the worklist. Wired into a new Phase 6.5 as a monthly sweep from launch day, and into GATE 6.
  2. **Dead-schema rule hardened from passive to active.** "`FAQPage` is OPTIONAL, skip it" advises the page being written and says nothing about pages already shipped — hence 18 live ones. Now an explicit REMOVE-IF-PRESENT directive with a detection one-liner, and **`HowTo` added to the dead list** (it was absent from the skill entirely while a live page emitted it). Also new: **check for a visible equivalent before deleting any schema node** — one page's two Q&As lived ONLY inside the JSON-LD, so a blind delete would have destroyed content, not just markup.
  3. **Locale rules promoted out of the geo/programmatic section into `references/core.md`** § "Secondary-locale localisation", where anyone building an ordinary bilingual site will actually find them — being buried in §8.14 is precisely why the warning went unread. Sharpened too: the flag alone is not enough, the switcher must READ it. The audited site had `hasAltLocale` set correctly on every page and still shipped 404s, because the language-switcher component never consulted it. One flag now governs hreflang, switcher and sitemap entry.
  4. **New rule: every shared nav/footer/CTA component derives hrefs from the current locale** — genuinely missing from the skill, and the largest defect found. `Nav.astro` and `Footer.astro` hardcoded English paths, so a reader on any `/cs/` page left Czech on their first nav click and never came back. Includes the allowlist trap: a hand-maintained `csMirrors` set that silently went stale the moment a new mirror shipped.
  5. **Orphan check caveated.** "No orphan pages" said nothing about how orphans get detected, and a crawl bounded to home + N pages reports every depth-3 page as one: **7 of the 8** URLs flagged on this audit were false positives. Rule now says treat crawl output as candidates and `grep` the repo for inbound links before restructuring navigation, since chasing a phantom orphan does real damage.
- v3.5: **Evidence-based SEO/AI-SEO overhaul, triggered by three research sweeps (~40 searches, primary sources) run after the owner asked what's actually proven to work.** Root cause of the sweep: several things this skill mandated as publish blockers had since been measured to do nothing, while the highest-evidence levers were missing entirely, and a site built to this skill's `robots.txt` template failed the adjacent indexing and AI-search skills' own checks on day one (it blocked `CCBot` while all of them required it unblocked). Five fixes:
  1. **`robots.txt` consolidated into one canonical template** — four tiers (classic search / AI retrieval bots / AI training bots / catch-all), the training-bot-≠-search-bot rule (blocking `GPTBot` doesn't touch `OAI-SearchBot`; 79% of publishers get this backwards [operating assumption — widely repeated, no primary source located]), and a crawler-delivery verification script. Keep the template in one place and generate every site's file from it, rather than hand-maintaining one per repo. Deployed across three live zones the same day; each was missing `ChatGPT-User`/`Claude-SearchBot`/`Claude-User`/`Bingbot`/`Googlebot` and still carried the deprecated `Claude-Web`. Also fixed a real bug found in the process: a private intake form was never actually disallowed live, because a past fix to the app repo's `robots.txt` had silently no-opped for months — an edge worker's exact-path route always wins over the app's catch-all route, so editing the repo file changed nothing. **Verify `robots.txt` by fetching the live URL, never by reading the file in the repo.**
  2. **`llms.txt`/`llms-full.txt` demoted from a GATE 5 publish blocker to an optional agent-tooling surface.** Ahrefs, n=137,210 domains: 97% of published files get zero requests, AI *retrieval* bots are 1.1% of the fetches that do happen, PerplexityBot logged 0 fetches across 556 domains in 12 weeks. Still built (cheap, and coding agents like Claude Code genuinely do fetch it — it out-fetched every AI retrieval bot combined in the Ahrefs data), just never gated on or sold internally as a citation lever.
  3. **Schema mandate cut from ~9 types to 5** (`Organization`, `BreadcrumbList`, `Article`/`BlogPosting`+author, `ProfilePage`+`Person`, in-person `Event`). `FAQPage` rich results were killed 7 May 2026 (SC reporting removed Jun 2026, API removed Aug 2026) and `Course` in June 2025; `Service`/`OfferCatalog`/standalone `WebSite` never had a live rich result. The only controlled experiment on record (Ahrefs DiD, 1,885 pages vs ~4,000 matched controls) found no significant AI-citation lift from adding JSON-LD, and −4.6% on AI Overviews. `dateModified` reframed from "top AI-citation lever" (unsupported — SearchPilot's own A/B was inconclusive, and Mueller called date-bumping "just lazy") to visible-date-shown, schema-only-on-genuine-change.
  4. **New §5.3 "Crawler delivery"** — the biggest gap the sweep found. AI-visibility run data showed one site serving an error to 54% of AI-crawler requests, concentrated on its most question-shaped content, while its `robots.txt` allowed every one of those bots the entire time — reading policy caught nothing; only fetching *as* the bot did. The crawler-delivery matrix now runs twice: once on staging (catches app-level 404s) and again on production after 6.3 (catches edge-level WAF/bot-fight/rate-limit failures staging can't surface), and the `/founder-pipeline:web-indexation` submission step is now hard-gated on the production run returning all-200.
  5. **Titles, internal linking, and content depth rewritten with real effect sizes** — these three are the only tactics in the whole sweep with genuine controlled-experiment evidence. Titles: 50–60 chars (Zyppy, n=80,959, lowest Google-rewrite band), causal backup +8.5%/+7% from two independent A/B tests. Internal linking: added the ≥1-exact-match-anchor rule (Zyppy, 23M links, ~5× traffic) plus causal confirmation (+7%/+5%/+25% across three tests). Content depth: new rule that money pages need real specifics, not just positioning copy (SearchPilot's largest 2025 effect, ~+20%), sequenced explicitly BEFORE internal-link-density scoring in Phase 5 — link counts over still-growing copy measure nothing.
  6. **Phase 5/6 re-sequenced by file zone instead of blanket `[S]`.** Both phase files previously marked nearly everything serial. New rule: parallelize by which files an item writes (Z1 standalone routes, Z2 layout `<head>`, Z3 page bodies, Z4 nav/footer, Z5 new pages), not by topic — and the old two-separate-staging-deploys pattern (GATE 5's external SEO-audit cycle, 6.1's Lighthouse/axe/forms cycle) merged into one deploy candidate with one parallel verification wave.
  Also reconciled with `/founder-pipeline:web-indexation`, `/founder-pipeline:ai-seo`, `/founder-pipeline:ai-seo-llms-builder` and `/founder-pipeline:seo-audit`: consistent `robots.txt`/`llms.txt`/meta-description-length/schema positions across every skill that touches them, one skill made the sole owner of AI-visibility baseline probing (replacing two duplicate manual-probe loops), and Bing elevated to a named launch blocker, because the large majority of ChatGPT and Copilot citations match Bing's top organic results [operating assumption].
- v3.4: **Per-page OG image now a mechanically-checked, sequenced step — not an unverified "auto-generated" placeholder.** Root cause: one money page shipped for a full day sharing the layout's generic hero photo as its social-share image — not because the meta tag was missing (it rendered fine), but because Phase 4's "auto-generated OG images" line described a runtime image-generation setup that was never actually built on any site in the estate; every real OG image was hand-designed from a gallery photo, and nothing forced every page to get one or caught the silent fallback. **The rule this produced is the general one: never let a phase file describe a capability nobody has built.** Three fixes: (1) `references/core.md` §7 rewritten from the fictional auto-generator recipe to the actual manual process — real event/community gallery photo (never stock), one reusable design-tool template (logo, eyebrow, 2-line headline, subtitle, gradient divider, location tags, photo right ~40%), 1200×630 `.webp` under 300KB at `public/gallery/<slug>/og-<slug>.webp`, wired via `ogImagePath`; (2) Phase 4's `[P]-safe` note now carves out the per-page OG image as the one sub-step that is NOT GATE-1-parallel — it bakes in the locked headline, so it waits for GATE 2 (voice pass + gallery in, the same state Design Review Round 2 already requires), avoiding rework when copy changes mid-build; (3) new mechanical "OG image coverage" script in `references/seo.md` (same pattern as the URL/canonical integrity script) greps every sitemap URL's built `og:image` for the fallback filename and fails the build on any hit — wired into GATE 4's exit criteria and Appendix F. This closes the gap the skill previously only caught at the sub-brand-layout level (§8.11's existing `ogImage` inheritance rule); the new checklist item generalizes it to every single page.
- v3.3: **URL/canonical integrity + llms.txt ordering.** Root cause: one section served every leaf at `/<section>/<slug>/` while each page declared `rel=canonical` at `/<section>/<slug>`, and that URL 307'd back — a canonical pointing at a redirect to itself. Search Console marked all 24 leaves "Alternate page with proper canonical tag", unindexable at the only URL the sitemap listed, unnoticed for months because the build was green. Four rules added: (1) Phase 5.1 — served URL === declared canonical, checked mechanically across ALL pages, script in `references/seo.md`; (2) Phase 5.1 — sitemap lists only canonical, indexable, 200 URLs, and anything excluded from the sitemap is excluded from the reindex queue too; (3) Phase 5.2 — `llms.txt` is BLOCKED until research round 2+ delivers the query list, keyword contract and FAQ, on the standing rule that llms files come after you know what people actually ask, plus `llms-full.txt` is the deep companion and never a copy, both files on every property or neither; (4) Phase 6 — re-point the Search Console sitemap submission at any cutover, since `robots.txt` naming a new sitemap does NOT update Search Console.
