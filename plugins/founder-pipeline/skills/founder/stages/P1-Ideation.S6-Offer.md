# P1.S6 — Offer: differentiators + solution → `P1-Ideation.S6-Offer.md`

**Phase: P1-Ideation**

**Earns its keep** always — this is where competition analysis (P1.S5) and demand data (P1.S4) become a concrete, differentiated offer. Differentiators and solution are one decision, not two: the onliness statement IS the value prop's unique mechanism, so they lock in one gate. **Becomes performative when** the offer already has one obvious, evidenced, ICP-valued differentiator and a locked scope — write the onliness statement + VPC and move on.

The uniqueness test is NOT global originality — it's **uniqueness within the territory and for the ICP**. Spine: Marty Neumeier's onliness statement:

> *"[Offer] is the ONLY [category from P1.S5] that [differentiator] for [ICP] in [territory]."*

If the sentence can't be filled truthfully, the offer doesn't have a differentiator yet — it has features.

**Ask one at a time (cap 6):**
1. Take the unique attributes from `P1-Ideation.S5-Competition.md` — classify each: unique **globally** / unique **in the territory** / merely **uncommon** / **table stakes**. Then fill the onliness statement from the survivors. Can every word survive a fact-check against competitors' websites? Evidence per surviving differentiator (`[source: ...]` per claim — countable and checkable, "412 onboarding audits shipped", not "deep experience").
2. Does the ICP actually CARE, and will it hold? Map each differentiator to a specific cited pain (from `P1-Ideation.S2-Problem.md` / intake / prediction discourse evidence), name its 12-month defensibility mechanism, and run the anti-claim check: which of your claims do competitors ALSO make? Those are entry tickets, not differentiators.
3. In one sentence, what is the offer? (concrete, no metaphors) — then the value prop one-liner: *"We help [ICP] do [job] by [unique mechanism], so they [enabled value]."* The unique mechanism must be a differentiator from Q1, not a new invention.
4. For each top-2 pain, what specific pain reliever / gain creator does the offer provide? (VPC 2-column table.)
5. What's NOT in the offer? Name ≥3 things buyers might expect that you're explicitly excluding. **Then two checks:**
   - **Catalog collision** — if the brand already sells anything (offer catalog, pricing page, partner packages), grep it for the same deliverables. The new offer must name its rung in the existing ladder and REUSE existing items as components, never re-describe them at a different price (in one run a new "done-for-you" offer nearly duplicated a package already in the brand's catalog).
   - **Promise backtest** — every numeric promise or guarantee (attendance, leads, results) names its exact metric definition (registered vs approved vs actually showed up; booked vs attended) and is backtested against the brand's own history: "this guarantee would have failed N of M past instances". Guarantee only on a metric that held in ≥ 90% of past instances; otherwise reword to the metric that did (worked example: a registrations guarantee held in all but one past event, while the same number as an in-the-room guarantee would have failed in more than half).
6. **Delivery capacity** (this step OWNS the capacity math — P2.S1, P2.S3, P2.S4 cite it): hours per client per month end-to-end (delivery + prep + admin) — derived from the founder's actual current calendar (named existing commitments + available weekly hours), tagged `[source: calendar <month>]`; quality ceiling at 5 / 10 / 20 clients; what breaks first; fulfillment model when it does (hire, productize, waitlist, raise price).

**Skills:** `/offers` (mandatory) to package the solution — scope shaping, risk reversal, guarantees — before the one-liner locks; `/scout` (mandatory) to verify nobody in the territory claims the same onliness — record the queries run + the 3 closest competitor claims (URLs) and why each does not match; if the anti-claim check needs competitor messaging pulled, reuse P1.S5's competitor files or re-read the rivals' own pages inline (no separate skill ships for this); `/brainstorm` if no differentiator survives and one must be designed (bundling, guarantee, delivery model, niche-down per the P1.S4 verdict).

**Write to** `P1-Ideation.S6-Offer.md`. Onliness statement + value prop one-liner at the top; differentiator table (Differentiator | Unique where | Evidence | ICP cares because | Durable via | Verdict); VPC 2-column table; exclusions; delivery-capacity block.

**Def-of-success — ALL must pass before owner sign-off (fail → improvement loop per SKILL.md, never advance):**
- `/critical` run recorded; the score is advisory — the gate is the criteria below.
- Onliness statement verified by recorded search evidence — `/scout` run mandatory; the file lists the queries run + URLs of the 3 closest competitor claims, with why each does NOT match the sentence.
- ≥ 2 differentiators unique at least within the territory/ICP, each with cited evidence, a mapped cited pain, and a named 12-month defensibility mechanism. Zero table stakes presented as differentiators.
- Value prop one-liner in format, unique mechanism = a locked differentiator, no metaphors.
- Every pain reliever maps to a cited pain (P1.S2/intake/P1.S4 evidence) — zero orphan features. ≥ 3 explicit exclusions.
- Catalog-collision check recorded (catalog path grepped + overlapping items named, or "no existing catalog"); every numeric promise/guarantee carries its metric definition and a backtest line "held in N of M past instances" with source — an untested guarantee is a FAIL.
- Delivery-capacity math complete (hours/client/month, ceiling at 5/10/20, what breaks, fulfillment answer); hours/client/month derived from the founder's actual current calendar (named existing commitments + available weekly hours), tagged `[source: calendar <month>]` — an untagged capacity number is a FAIL.

**Gate out (mandatory — see SKILL.md house rules):**
1. Draft `P1-Ideation.S6-Offer.md`.
2. Invoke `/critical` — attack the onliness statement and the capacity math hardest: is it unique or just unverified? Would the ICP pay for this difference or merely nod? Is the hours-per-client number honest?
3. Revise; note what changed.
4. Present to the owner. **Wait for their explicit approval. Never auto-advance.**

**Checkpoint:** "Offer locked: [one-liner]. Onliness: [X]. Capacity: [N]h/client, ceiling at [M]. These feed pricing power and every line of copy downstream. Name next — or test the concept against 2 accounts from `accounts.md` first?"
